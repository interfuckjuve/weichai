# 第一章 项目概述

## 1.1 项目简介

RECAST 是一套面向大型工业软件的代码检索与开发辅助平台。系统解析代码仓库，建立符号索引和依赖关系，根据开发人员或编程智能体提出的需求，查找相关实现、接口和配置，并返回对应源码、文件位置及版本信息。

大型工程中的一项功能通常分散在多个文件中。编程智能体即使找到入口函数，也可能需要继续查找调用方、数据类型和配置项。RECAST 预先完成可以重复使用的源码解析和索引工作，再按任务读取相关内容，减少智能体反复搜索和阅读文件的次数。

项目面向百万至千万行、多仓库和多语言工程开展研发，支持功能定位、代码修改、软件迁移和系统维护。这里的规模与语言范围是建设和评测目标，当前实现范围及已有实验结果见第八章。

## 1.2 项目定位

RECAST 为现有 AI Coding 工具提供代码查询服务。系统负责保存源码版本、提取声明、分析依赖和维护索引；Coding Agent 根据查询结果制定修改方案、生成代码并执行验证。

接入仓库后，系统分别保存模块、文件、类型和函数信息。收到查询时，先结合关键词、符号名称和语义相似度查找候选，再补充理解这些代码所需的接口、类型和配置。返回内容按照模型输入长度限制进行筛选，并标明哪些依赖尚未解析、哪些内容因长度限制而省略。

因此，开发人员不仅能看到匹配的代码，还能检查它属于哪个版本、与哪些实现相连，以及现有信息是否足以支持修改。

## 1.3 核心应用场景

RECAST 主要面向大型制造、能源、交通、金融及央国企的软件研发部门，也适用于承担遗留系统改造的软件集成商和维护多仓库产品的平台团队。主要场景包括：

（1）根据自然语言需求，在大型仓库中定位相关模块、文件、类型和函数。

（2）查找多套业务系统中的重复功能，为系统精简和功能合并提供参考。

（3）在语言、框架或平台升级前查找可复用实现，并识别迁移所需的依赖。

（4）根据需求、接口、代码片段或错误日志检索企业内部已有代码。

（5）修改公共接口或基础模块前，查找跨仓库、跨模块的调用方。

（6）在 Java、ArkTS、Kotlin/KMP、C/C++ 等混合工程中分析跨语言调用和注册关系。

（7）向 Coding Agent 返回相关源码及其位置、版本和依赖，供其继续分析与修改。

## 1.4 项目建设目标

项目需要同时解决大规模建库、任务定位和依赖补充三个问题。索引必须能够随源码变化更新，查询必须在限定时间内找到相关实现，返回内容还应包含修改所需的接口和配置。具体目标如下：

（1）在百万至千万行工程上建立可增量维护的代码索引，测量建库时间、内存与更新开销。

（2）支持 Java、ArkTS、Kotlin Multiplatform、C/C++ 等语言，分别验证语法解析、语言内名称解析和跨语言关系。

（3）统一记录跨文件、跨模块和跨语言依赖，使每条关系可以追溯到源码或构建配置。

（4）根据自然语言需求查找代码，兼顾召回率、排序准确性和查询时延。

（5）在 token、文件数和源码行数限制内选择必需内容，减少重复片段。

（6）通过 MCP、HTTP 和 IDE 接口向不同 Coding Agent 提供查询功能，并检验其对后续修改的实际帮助。

## 1.5 项目总体能力

系统管理仓库、分支和分析版本，识别源码、构建文件、接口声明、配置及测试。解析结果按模块、文件、类型和函数组织，全文索引负责词法匹配，向量索引用于查找语义相近的内容，依赖关系用于补充相关实现。

查询可以包含自然语言、代码片段、符号名称、接口签名、异常日志或文件路径。系统合并不同索引的候选结果，再按照工程范围、语言和接口要求筛选。需要进一步分析时，通过依赖查询补充调用方、被调用函数、类型或配置。

最终返回的数据包括入选源码、来源版本、文件位置和依赖说明。下游 Agent 可以直接查看这些内容，也可以针对未解析或省略的部分继续查询。

## 1.6 项目当前阶段

目前已有原型能够完成仓库接入、源码分析、模块划分、任务检索和结果展示。当前代码还接入了受限并行解析、模块分析结果恢复、部分跨语言绑定，以及多文件生成后的固定行为测试。

这些实现已通过固定样例和功能测试，但还不能据此认定完整 SDK 语义、千万行规模或未知开发任务的效果已经达标。现阶段重点是补齐跨语言分析的适用场景，检查大仓中的建库和查询开销，并完善前端与翻译后端的操作流程。

后续将在固定硬件、数据库、模型和任务集上测量检索准确率、响应时间、依赖覆盖率，以及代码修改后的行为通过率。已有结果和待开展实验分别列于第八章。

# 第二章 背景与需求分析

## 2.1 行业背景与国家战略需求

### 2.1.1 国产软件与操作系统生态发展

国产操作系统和企业数字化系统的发展带来了平台适配、系统整合和技术栈升级需求。企业已有业务代码往往分散在不同部门、仓库、分支和技术栈中，研发人员需要先确认某项功能是否已经实现，再判断现有接口和运行环境能否满足新的需求。

重新开发全部功能会重复已有工作，直接复制旧代码又可能遗漏依赖。软件迁移因此需要先理解原有实现，再确定可以复用的部分和必须修改的部分。

### 2.1.2 AI Coding 技术发展趋势

AI Coding 已从代码补全和单文件生成扩展到多文件修改、错误修复和软件迁移，但代码生成能力并不能代替工程中的功能定位和依赖分析。

大模型无法在一次输入中读取百万行乃至千万行源码。按固定长度切块容易切断函数及其关联定义，逐文件搜索又会增加模型调用和读取时间。因此，需要预先建立可查询的代码索引，再按任务提供相关源码。

### 2.1.3 超大规模软件工程智能化需求

大型工业软件通常包含较多模块、技术栈和历史版本。一项修改可能涉及不同文件甚至不同语言。LSP 和字符串检索适合导航到已知符号，但反射、依赖注入、运行时注册及配置驱动的调用还需要其他分析方法。

向量相似度可以找到功能描述接近的代码，却不能说明它们是否使用相同接口、平台或依赖。要把检索结果用于修改和迁移，还需核对这些工程条件。

## 2.2 命题企业与业务背景

### 2.2.1 命题企业相关业务背景

本项目面向华为提出的“AI Coding 超大工程代码理解与快速索引”相关产业需求。研发人员需要在百万至千万行工程中，为新增、修改、删除、迁移和维护任务确定实现位置及相关依赖。

HarmonyOS 等软件生态中的多语言、跨模块和跨平台特征增加了分析难度。查询系统既要处理代码规模，也要识别上层接口与底层实现之间的连接方式。

### 2.2.2 大型软件工程与代码迁移场景

一个业务功能可能同时涉及入口、Service、Repository、公共数据结构、配置、Native 模块和测试。在 Java、ArkTS、Kotlin/KMP、C/C++ 混合工程中，它们还可能通过 JNI、N-API、接口声明或构建配置连接。

因此，开始生成目标代码之前，需要明确原功能由哪些文件共同实现、调用哪些接口、依赖哪些配置，以及哪些行为必须保留。只翻译入口函数容易遗漏这些条件。

## 2.3 命题需求分析

### 2.3.1 命题总体目标

赛题要求支持 Java、ArkTS、Kotlin Multiplatform、C/C++ 等语言的代码理解与检索。代码检索准确率目标不低于 90%，平均检索时间控制在 10 秒以内；对接 AI Coding 后，转换或生成代码的功能完备度目标不低于 90%。

这些数值需要在统一测试集和运行环境下验证，不能以少量演示用例通过代替正式验收。

### 2.3.2 命题指标拆解

百万至千万行规模要求索引能够在受控资源内构建和更新。多语言支持要求分别检查声明解析、名称解析和跨语言依赖。检索准确率要求自然语言需求能够定位到有效实现，时延要求则限制候选搜索、源码读取和结果整理的总开销。

功能完备度还要求将检索与后续修改一起验证：即使排名靠前的函数与需求相关，遗漏类型、配置或异常处理仍可能导致生成代码行为错误。

### 2.3.3 命题本质分析

给定一个自然语言开发任务，系统需要从大型工程中找到相关实现，补充修改所需的依赖，再在模型输入上限内整理这些内容。

这一过程对应四项工作：建立并维护代码索引，分析调用与绑定关系，查找与需求相关的实现，以及筛选供 Agent 阅读的源码。四项工作需要使用相同的工程范围和源码版本。

## 2.4 典型业务场景

### 2.4.1 功能定位场景

开发人员可能只知道需求，不知道函数名或文件位置。例如，“查找登录失败后转换为 HTTP 401 的处理逻辑”可能对应异常处理器、鉴权模块或网关组件，代码名称未必包含完整需求表述。

系统需要结合描述、符号和调用关系找到实现，并给出可以直接查看的源码位置。

### 2.4.2 代码迁移场景

类型系统、异常处理、并发模型、数值精度、内存管理和框架约定的差异，可能使迁移后的代码能够编译却无法保持原有行为。

迁移时需要核对接口、调用关系、数据结构、配置和测试，并记录代码来源、修改范围及验证结果，便于检查遗漏和恢复原文件。

### 2.4.3 大型工程修改场景

修改公共接口或基础类型时，影响范围可能跨越多个模块或语言。只读取目标文件容易遗漏调用方、实现类和配置，读取整个工程又会增加模型输入。

系统需要从被修改对象出发查找相关使用者，返回可能受影响的源码，并说明分析尚未覆盖的关系。

## 2.5 现有 AI Coding 工作方式分析

通用 Coding Agent 通常通过多轮搜索和读取逐步了解陌生工程：先查找关键词，读取命中文件，发现新的符号后继续搜索，再根据获得的信息制定修改方案。

这种方式便于根据新发现调整方向，但仓库规模和语言种类增加后，搜索与读取次数也会上升。上下文过少会遗漏关键类型和配置，过多则会包含重复或无关内容。

预先维护代码索引可以减少重复扫描；根据依赖关系补充源码可以减少部分人工探索。两者仍需通过任务测试检查是否减少了读取次数并保留了必要信息。

## 2.6 现有技术方案及其局限

### 2.6.1 关键词与全文检索

关键词、字符串和正则检索适合查找已知文件名、函数名、错误码或固定字符串，结果也容易核查。但用户表述与标识符不一致时，词法匹配可能漏掉相关实现。

### 2.6.2 LSP 与符号检索

LSP 和编译器符号索引可以查找定义、引用与类型，通常需要先确定一个已知符号。跨语言桥接、运行时注册和配置驱动的关系还受到语言服务及构建环境限制，不能假定单一 LSP 可以完整分析。

### 2.6.3 向量语义检索

向量检索将需求和代码说明编码为向量，能够在命名不同的情况下找到功能相近的实现。但相似代码可能属于不同调用路径、平台或模块，仍需检查接口和依赖是否适用。

### 2.6.4 传统 RAG

普通代码 RAG 常将源码按固定长度切块，建立向量索引后返回排名靠前的片段。固定切块可能截断函数或类型，也难以同时满足局部修复与模块迁移所需的不同范围。

### 2.6.5 Coding Agent 多轮探索

Agent 能够根据新发现继续搜索和读取文件，但搜索方向取决于当前已获得的信息。在大型仓库中，这可能带来重复读取或遗漏依赖，需要记录调用次数、耗时和最终任务结果来判断效果。

## 2.7 核心技术难点

### 2.7.1 超大规模代码仓建模

在可接受的时间和内存内解析大型工程，保存可局部查询的索引，并在源码变化后减少重复处理。

### 2.7.2 跨语言跨模块依赖分析

根据声明、注册项和构建配置识别关系，保存对应位置；无法确定的目标保留未解析状态，避免错误连接。

### 2.7.3 高精度低延迟代码检索

结合词法、符号、语义和模块信息选择候选，在召回相关实现的同时限制搜索范围、读取量和查询时间。

### 2.7.4 模型输入中的源码选择

从候选中选出当前任务必需的实现、接口、配置、类型和测试，合并重复范围，并核对最终文本的 token 数。

# 第三章 市场现状与竞品分析

## 3.1 市场供给现状

相关产品主要包括代码搜索与导航平台、规则化重构与迁移平台、特定技术栈升级工具，以及通用 Coding Agent。它们分别侧重大仓查询、批量代码变换、固定升级流程和自然语言交互。

RECAST 的研发重点是根据任务查找实现、补充依赖并整理模型输入。与现有产品比较时，需要分别检查索引规模、可分析的关系、查询效果和修改结果，不能仅比较功能名称。

## 3.2 主要产品对比

| 产品 | 主要能力 | 本项目需要比较的内容 |
| --- | --- | --- |
| Sourcegraph | 支持多仓库关键词、正则、符号、提交和差异搜索；SCIP 索引用于定义与引用导航，精确索引不可用时可使用搜索式导航 | 比较索引规模、查询时延和关系查询；另测自然语言需求能否定位有效实现，以及是否返回所需依赖 |
| GitHub Copilot | 结合仓库内容回答问题和执行编码任务，并接入代码托管与开发协作流程 | 比较任务所需的搜索与读取次数、上下文中重复内容、来源标注及最终修改结果 |
| Moderne / OpenRewrite | OpenRewrite 使用 Lossless Semantic Tree 和确定性 recipe 执行升级、修复与重构；Moderne 支持多仓库执行和管理 | 对已知变换规则的任务比较正确率与批量处理效率；对需先查找参考实现的任务，比较定位与适配效果 |
| Amazon Q Developer | 为受支持的 Java 和依赖版本升级提供自动化流程，结合构建、差异查看和人工接受完成迁移 | 在共同支持的升级任务上比较结果；多语言工程另行说明适用范围，避免将不同任务的指标直接对比 |

## 3.3 竞争判断

Sourcegraph 主要提供大规模代码搜索与导航，Moderne 和 OpenRewrite 擅长按确定规则执行批量变换，Amazon Q Developer 提供部分技术栈升级流程，通用 Coding Agent 则能根据自然语言灵活调用工具。

RECAST 尝试将大型工程索引、跨语言依赖分析和按任务选择源码结合起来。是否优于已有产品，需要在共同支持的任务和相同条件下测量；目前不能仅凭设计方案认定这些组合已经形成效果优势。

## 3.4 项目差异化方向

首先，检索需要找到承担目标功能的实现，即使命名与用户需求不同。其次，排序时检查调用关系、类型、构建条件和目标接口，减少语义相近但无法用于当前工程的结果。

检索结果还应包含必要依赖、来源版本和文件位置，并说明尚未解析或因长度限制而省略的内容。这样，开发人员可以核查结果，Agent 也可以继续查询缺少的信息。

系统与 Agent 分别承担可重复的索引处理和具体任务判断。解析、关系记录及基础查询由系统执行，模型在较小的候选范围内分析适用性并生成代码。

## 3.5 竞品对标方法

对比采用相同的脱敏多语言仓库、需求查询、硬件和超时策略。检索报告 Recall@K、Precision@K、MRR、nDCG、平均时延和 P95；依赖分析按关系类型报告准确率、召回率及跨模块路径完整度。

上下文评价记录必需代码覆盖率、重复内容比例、token 数和后续任务成功率。对不开放底层索引接口的产品，只比较能够直接观察和复现的结果，并注明产品版本与测试日期。
