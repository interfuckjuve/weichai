# 华为真实需求与现有工作流对照

更新时间：2026-09-06。实现基线：`main`，`3d8e0ff`。

需求来源：[企业需求原图](86a914508be2892643ab60c1feeb6a05.jpg)，题目为“面向 AI Coding 超大工程的代码理解与快速索引方法”。本文区分原文明示的要求、据此推导的工作流和现有代码能力；推导部分不是企业已经确认的接口规范。

## 1. 核心判断

华为需要的是服务于 AI Coding 的大工程代码理解与上下文检索能力：AI 在生成、翻译或修改代码时，能快速取得相关实现、接口和依赖，减少上下文缺失造成的功能遗漏与错误。

我们目前的主线是：选择目标模块，描述需求，从历史仓库中召回模块候选，再由用户检查文件、接口和代码预览。这覆盖了“寻找可复用模块”的一部分需求，但还没有完整覆盖“为编码任务定位修改位置、补齐依赖上下文，并结合生成和测试反复检索”的流程。

因此，模块到模块匹配可以保留为复用入口；面向企业需求，还需要任务到代码上下文的入口。后者不要求用户预先知道应该修改哪个模块，也不要求每次都从历史仓库查找。

## 2. 工作流并排对照

下表按一次编码任务的处理顺序排列。企业侧描述是依据原文推导的合理工作流，不是原图逐项规定的操作步骤。“部分具备”表示已有相关实现，但尚未完整接入或未完成业务验收。

| 步骤 | 华为需求对应的工作流 | 我们现在的工作流 | 差距判断 | 具体缺口 |
| --- | --- | --- | --- | --- |
| 1. 确定任务 | 提出需求迭代、代码翻译或增量开发任务；可只有需求，也可指定代码位置 | 先选择目标工程中的模块，再输入需求；另有类、函数入口 | 部分具备 | 缺少“只有需求、尚不知道修改位置”时的任务定位入口 |
| 2. 接入工程 | 接入大型源工程及必要的目标工程、平台和构建上下文 | 显式选择目标工程，配置历史仓库；按仓库和版本登记 | 部分具备 | 源与目标平台约束尚未成为模块检索的完整结构化输入 |
| 3. 理解代码 | 分析 Java、ArkTS、KMP、C/C++ 等工程，定位实现及显式、隐式依赖 | Tree-sitter 提取多语言结构；Java/C# 有独立编译器增强通道，主要由模块迁移入口触发 | 差距明显 | 企业要求的语言和构建语义未补齐；JNI、Node-API、KMP 绑定及框架回调桥接未实现 |
| 4. 建立并维护索引 | 支撑百万、千万行级工程解析和索引；代码变化后及时更新 | SeekDB 保存结构事实和检索文档；支持文件增量复用、模型向量缓存和版本隔离 | 部分具备 | 未完成企业规模实测；部分分析仍读取全量结构；历史版本和中断记录缺少自动回收 |
| 5. 触发检索 | 开发者或 AI 在规划、修改、翻译、排错时按需发起查询 | 主界面等待项目模块分析完成后，按目标模块和需求检索历史模块 | 差距明显 | 主检索范围限于历史仓库；尚无统一的任务阶段驱动检索循环 |
| 6. 定位相关代码 | 找到需要理解或修改的位置，以及可复用实现；可以在当前工程内查找 | 模块三视图描述经全文和向量召回、归并排序，返回 Top-K 模块 | 部分具备 | 相似模块查找不能替代修改位置定位；真实模型需配置启用，默认 hash 不是学习得到的语义表示 |
| 7. 补齐上下文 | 沿依赖关系补充调用方、被调用方、跨语言端点、关联测试和配置 | 返回完整模块文件清单、声明接口、依赖模块 ID；预览最多 3 文件，每文件 4,000 字符 | 差距明显 | 没有围绕任务自动扩展必要依赖、调用链、测试和构建配置；完整清单不等于完整源码上下文 |
| 8. 控制模型输入 | 在有限上下文长度内，优先提供完成当前任务所需的信息，并保留来源 | 限制候选数、查询长度和预览长度；检索结果绑定仓库、版本和证据 ID | 部分具备 | 现有限长主要是固定截断，尚无基于任务重要性、覆盖范围和 token 预算的上下文选择 |
| 9. 生成或翻译 | 将检索上下文提供给 AI Coding，依据同一 Spec 生成或转换代码 | 类、函数路径已有适配；主界面明确阻止模块候选进入单文件适配 | 主模块流程未接通 | 模块候选到完整多文件源码包、生成和适配的连接尚未完成 |
| 10. 验证与补查 | 构建、测试检查功能完成情况；根据失败继续定位和检索，再修正代码 | 另有独立模块迁移命令，支持导入本地补丁包、隔离 Git worktree 验证和审阅提交 | 部分具备 | 独立补丁验证能力未与主模块检索连接；尚未形成“检索—生成—验证—再检索”的闭环 |
| 11. 判断业务效果 | 检索准确、响应快速，并提高相同 Spec 下的生成或转换功能完备度 | 已有验收定义、小样本真实模型/数据库验证、增量和界面检查 | 尚未完成企业验收 | 缺少企业独立标注任务、真实规模工程与冻结 Spec，不能据小样本声称业务达标 |

主要差距集中在三处：多语言真实依赖的还原、任务所需上下文的组织、检索与生成验证的连接。继续只优化候选排序，不能单独补齐这些流程缺口。

## 3. 原文明示的业务背景和要求

原文明确提及应用鸿蒙化，通过代码翻译或代码生成补齐鸿蒙端能力，使用场景包括智能需求迭代、批量代码翻译和增量功能开发。

原文列出的核心问题包括：

- 大型代码仓的解析和索引效率存在瓶颈。
- 多语言场景的调用链难还原，客户端特殊架构可能形成隐式代码依赖。
- 大模型上下文有限，无法一次装入完整工程。
- 字符串和文本匹配噪声大、定位不准，导致需求理解偏差和生成准确率低。

原文要求构建轻量、可落地、可复用的代码索引与检索工具，方法不限于知识图谱、向量化、混合检索。它明确提出支持 Java、ArkTS、KMP、C/C++ 等代码理解与检索，代码检索准确率至少 90%，检索平均耗时在 10 秒以内，生成或转换后的代码功能完备度超过 90%。

原图未规定检索准确率的分母、Top-K、负例比例、测试并发及功能完备度的计算方式。我们的模块命中率、服务内部超时预算和单元测试通过率，均不能直接替代这些业务指标。

## 4. 检索发生在哪些场景

| 场景 | 检索触发时机 | 输入示例 | 希望得到的结果 | 与现有模块匹配的关系 |
| --- | --- | --- | --- | --- |
| 已有功能迁移或翻译 | 已确定要迁移的功能，准备理解源实现和目标接入方式时 | 指定源模块，给定目标平台、语言和必须保留的行为 | 源实现、必要依赖、跨语言连接、相关测试、目标侧接口和接入位置 | 相似历史模块可作为参考，但指定源模块时更需要依赖提取，不一定需要重新找相似模块 |
| 新增功能 | 已知功能要求，但不清楚现有能力和实现位置时 | “给下载功能增加断点续传”，附当前工程和平台约束 | 可复用能力、参考实现、扩展位置、接口和调用方式 | 历史模块召回覆盖了参考实现查找；当前工程定位和上下文补齐仍有缺口 |
| 已有功能迭代 | 修改现有行为，需要判断影响范围时 | 修改要求、已知入口或文件、兼容性要求 | 实现位置、调用方、被调用方、受影响模块、配置和回归测试 | 主要是影响分析，不能只依靠历史模块相似度排序 |
| 生成后的问题定位 | 编译或测试失败，需要补充信息时 | 错误信息、失败测试、已修改文件和版本 | 缺失接口、错误调用位置、相关实现和测试约束 | 是支撑前三类任务的反馈步骤，目前未接入主模块检索闭环 |

“断点续传”是解释检索过程的示例，不是企业原图指定的任务。生成后补查是从 AI Coding 完整流程推导出的设计建议。

## 5. 检索输入应该是什么

用户可能只输入一段需求，其余信息应由 IDE 或 Agent 从当前任务中补齐，不应要求用户填写所有字段。

| 输入项 | 具体内容 | 是否必须由用户提供 | 当前模块检索情况 |
| --- | --- | --- | --- |
| 任务目标 | 新增、修改、翻译或迁移什么功能 | 通常需要描述，或来自已有 Spec | 有自然语言 requirement |
| 工程范围和版本 | 允许搜索的仓库、项目及代码版本 | 工程由用户选择，版本由系统绑定 | 有历史仓库范围和活动版本检查 |
| 已知代码位置 | 文件、函数、模块或入口；未知时允许为空 | 可选，也可来自 IDE 当前选择 | 主界面要求先选目标，尚不支持纯需求自动定位模块 |
| 平台和语言约束 | 目标平台、语言、必须保持的接口和允许依赖 | 用户与工程配置共同提供 | 有目标语言等元数据，但未完整作为结构化检索约束执行 |
| 当前子任务 | 定位实现、找参考、提取依赖、分析影响或修复失败 | 可由 Agent 产生 | 主模块入口以寻找历史实现为主 |
| 已有上下文 | 已读代码、已知依赖、已修改内容，避免重复返回 | 系统提供 | 尚无统一的多轮任务上下文状态 |
| 返回预算 | 允许多少条结果、代码长度或 tokens | 通常由系统决定 | 有 Top-K、查询时间和预览限长；尚无任务化 token 分配 |

目前主模块查询实际拼接目标名称、签名、说明、需求和核心 API，主要搜索历史模块摘要。它没有把目标完整源码、平台硬约束和依赖图统一转换为检索条件。

## 6. 检索输出应该是什么

内部可以先召回 Top-K 候选，但最终交给 AI 的结果应是一份任务上下文：哪些代码值得读、与任务有什么关系、还缺哪些信息，以及如何继续查询。

| 输出项 | 对编码任务的作用 | 当前实际输出 |
| --- | --- | --- |
| 主要实现或修改位置 | 告诉 AI 从哪里开始改 | 有候选模块身份和文件清单；不等于已定位当前工程修改位置 |
| 相关实现代码 | 提供可理解、可参考的具体实现 | 有部分源码预览；未形成完整模块源码包 |
| 必要接口和依赖链 | 防止只复制主体代码而漏掉依赖 | 有核心 API 和模块依赖 ID；缺少任务相关的自动依赖展开 |
| 跨语言连接 | 说明两种语言的实现如何关联 | 尚未实现企业所需桥接分析 |
| 行为与平台约束 | 保留错误处理、生命周期、线程和接口要求 | 当前接口名称匹配不验证这些行为 |
| 关联测试和构建配置 | 为生成后的验证提供依据 | 模块匹配结果未自动组织这些内容 |
| 来源和不确定性 | 支持复查，避免使用过期或未经确认的信息 | 有仓库/版本/项目/模块身份、证据 ID、缺失接口和预览截断标记 |
| 后续查询线索 | 当前预算不足时继续按需读取 | 有底层语义查询能力，但尚未与主匹配流程形成完整的多轮上下文协议 |

### 示例：新增断点续传

假设用户提出“在现有下载功能中增加断点续传，保持公开接口不变”。合理的检索过程应先定位下载入口、任务调度和网络请求实现，再补充已有的 Range 请求处理、进度持久化、完成回调及相关测试。

返回结果需要说明各文件承担什么角色，例如“这里创建请求”“这里保存偏移量”“这个回调触发界面状态更新”。如果调用经过原生层，必须继续定位绑定端点，或明确标记关系尚未确认。

我们现在更可能返回一个名称或职责相近的历史下载模块。这可以提供参考，但还不能据此判断当前工程应该修改哪些文件、保留哪些接口、执行哪些回归测试。

## 7. 现有能力怎么复用，下一步怎么补

| 优先事项 | 可以直接复用的部分 | 需要新增或接通的部分 | 具体完成标志 |
| --- | --- | --- | --- |
| 建立任务上下文契约 | 仓库版本、模块身份、需求和证据结构 | 任务类型、已知位置、平台约束、上下文预算及角色化输出 | 同一请求能表达“找参考模块”和“定位当前修改点”，输出说明每份代码的用途 |
| 补齐当前工程检索 | 模块三视图、全文/HNSW 召回、可选重排 | 当前工程范围查询、已知位置导航、需求到代码位置定位 | 无需预先选定模块，也能从真实需求定位应修改的实现 |
| 组织依赖上下文 | 结构依赖、语义查询、代码范围和证据 ID | 按任务展开调用关系、测试及配置，按预算选取内容 | 返回上下文足以解释核心实现和必要依赖；缺失部分显式可见 |
| 完善多语言适配 | 语言注册、Tree-sitter、编译器增强与 LSP 接口 | 企业指定语言的构建语义、跨语言绑定和框架关系 | 用可构建工程验证每类关系，区分确认、推测和未知 |
| 接通生成验证 | 既有适配服务、模块补丁包、worktree 验证与审阅 | 主检索结果到多文件生成，以及失败后的补查和修正 | 一个真实任务从需求到检索、修改、测试、审阅跑通 |
| 用企业数据验收 | 已有脚本、性能统计和版本记录 | 独立任务标注、真实规模工程、冻结 Spec 和明确指标 | 能比较检索前后同一编码任务的结果，而非仅报告候选命中 |

以上是适配方向，不表示这些补齐项已经实施。真实 embedding 和重排已接入但需要配置启用；默认 hash 向量不具备学习得到的跨语言语义能力。小样本验证也没有证明系统达到企业要求的检索准确率或功能完备度。
