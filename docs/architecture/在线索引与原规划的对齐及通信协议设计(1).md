# 在线索引与原规划的对齐及通信协议设计

**日期：** 2026-09-08  
**作者：** Manus AI

## 结论

团队报告与原规划并不冲突，但两者关注的对象不同。

团队报告主要解决：

```text
如何对超大代码仓进行有界、可恢复、可增量的索引构建，
并生成文件、符号、依赖、代码块和分层模块树。
```

原规划主要解决：

```text
Agent 收到自然语言任务后，如何选择索引、召回候选、扩展关系、
控制 token 预算，并生成带源码证据的最小上下文。
```

因此，团队现在做的“在线索引”如果指的是**在线可查询的索引服务**，它是原规划中的数据平面；如果指的是**系统运行期间持续构建或更新索引**，它则是离线分析与在线服务之间的增量发布流水线。两种含义需要在协议中明确区分。

推荐的总边界是：

```text
源码快照与构建上下文
        ↓
离线/后台索引构建
        ↓ 发布不可变索引快照
在线索引数据服务
        ↓ 提供基础查询
在线检索编排与 Context Compiler
        ↓
MCP / HTTP / CLI / IDE
```

团队报告已经覆盖了前两层的大部分内容，并部分覆盖了分层表示和路由元数据；原规划还需要补齐在线检索策略、关系图查询、上下文编译、统一响应和 Agent 包装层。

## 1. 两份规划的职责差异

| 能力 | 团队报告 | 原规划 | 当前判断 |
|---|---|---|---|
| 固定源码快照 | 已覆盖 | 必须 | 团队报告可作为事实来源 |
| 流式扫描与背压 | 已覆盖 | 基础要求 | 直接采用 |
| Tree-sitter 解析 | 已覆盖 | 结构索引层 | 直接采用 |
| 文件、符号、引用落库 | 已覆盖 | 基础索引层 | 直接采用 |
| 轻量依赖概览 | 已覆盖 | 图搜索的输入 | 需要明确证据和置信度 |
| 语义依赖图 | 由队友提供 | Code Graph 层 | 通过 `graphRevision` 消费 |
| SCIP/compiler index | 报告未作为核心实现 | 精确符号层 | 可作为后续能力，不应阻塞首版 |
| 代码块索引 | 已覆盖 | symbol region 层 | 直接采用 |
| 叶模块和上层模块 | 已覆盖 | Context Compiler 的摘要材料 | 直接采用 |
| 多粒度向量投影 | 已覆盖 | 语义召回层 | 直接采用，但单独版本化 |
| 检索粒度选择 | 分层表示可复用 | 用户请求与 Query Planner 的输入 | 显式选择主要结果粒度；仅自动模式由系统判断 |
| 在线词法检索 | 部分涉及 SeekDB | 原规划中的 lexical layer | 需要定义查询 API 和快照绑定 |
| 在线符号检索 | 部分涉及 | 原规划中的 symbol layer | 需要明确 symbol identity 和分页 |
| 在线图扩展 | 由 GraphStore 提供 | 原规划的核心 | 需要补充 `expand`、`trace` 契约 |
| Query Planner | 未覆盖 | 原规划核心 | 另设在线编排模块 |
| Reranker | 未覆盖或由下游负责 | 原规划核心 | 另设在线策略模块 |
| Context Compiler | 由下游负责 | 原规划核心 | 必须定义输入输出协议 |
| MCP/HTTP/CLI 包装 | 未覆盖 | 原规划包装层 | 另设 gateway |
| 结果证据与版本一致性 | 已有基础字段 | 原规划硬要求 | 统一身份协议即可衔接 |
| 取消、重试、租约、发布 | 已覆盖 | 运行保障要求 | 直接采用，但区分任务状态和发布状态 |

## 2. 最重要的概念区分

### 2.1 索引构建不等于在线索引服务

团队报告中这些任务属于**索引构建平面**：

```text
scan-partition
parse-partition
bind-references
partition-module
summarize-module
embed-batch
publish-revision
```

它们负责产生数据。

以下能力属于**在线查询平面**：

```text
searchLexical
searchSymbols
getModuleOverview
getSymbol
getRelations
expandGraph
tracePath
fetchSource
compileContext
```

它们负责消费已经发布的数据。

不要让在线查询直接读取 `building` 状态的数据，也不要让离线 worker 直接决定 Agent 一次请求返回多少 token。两边通过不可变 revision 和 manifest 解耦。

### 2.2 在线索引的两种含义

为了避免团队沟通歧义，建议使用以下术语：

| 术语 | 定义 |
|---|---|
| `index build` | 解析代码并生成索引数据的过程 |
| `index publication` | 将已校验的索引生成版本发布为可读快照 |
| `online index service` | 对已发布索引提供低延迟查询的服务 |
| `working tree overlay` | 对未提交源码使用 ripgrep/LSP 提供的临时覆盖层 |
| `retrieval orchestration` | 根据用户任务选择索引、扩展图和编译上下文的在线策略 |

团队现在最适合优先做的是：

```text
流式 index build + 不可变 index publication + 基础 online index service
```

还不能称为完整的 Agent 在线检索系统，除非同时实现 retrieval orchestration 和 context compilation。

## 4. 版本身份协议

所有在线和离线接口都必须携带以下身份。它们不能被合并成一个字段。

| 字段 | 含义 | 责任方 |
|---|---|---|
| `repositoryId` | 仓库逻辑身份 | 仓库注册/平台 |
| `sourceRevision` | Git ref、tree 或 commit 来源 | 快照管理 |
| `analysisRevision` | 一次结构分析输入版本 | 基础分析块 |
| `graphRevision` | 关系图版本 | GraphStore |
| `buildProfileId` | 构建配置身份 | 构建上下文服务 |
| `buildContextId` | 具体编译单元或语言服务上下文 | 编译分析器 |
| `treeRevision` | 模块树不可变发布版本 | 模块树服务 |
| `treeInputHash` | 生成模块树的所有输入摘要 | 模块分析器 |
| `projectionRevision` | 搜索投影版本 | SeekDB/向量/全文投影 |
| `indexGeneration` | 在线服务实际读取的组合索引代次 | 发布协调器 |
| `workingTreeRevision` | 未提交工作区覆盖版本，可为空 | Host/IDE |

推荐的组合快照如下：

```json
{
  "repositoryId": "payment-monorepo",
  "sourceRevision": "git:abc123",
  "analysisRevision": "analysis_20260908_001",
  "graphRevision": "graph_20260908_004",
  "buildProfileId": "linux-x64-prod",
  "buildContextId": "typescript-tsconfig-prod",
  "treeRevision": "tree_20260908_002",
  "projectionRevision": "projection_20260908_003",
  "indexGeneration": "generation_20260908_007"
}
```

`indexGeneration` 表示在线查询时的最终组合视图。它必须指向一组已经通过兼容性校验的基础索引、图、模块树和投影，不能只表示某一个数据库表的版本。

## 6. 在线查询协议

### 6.1 `SearchRequest`

以下粒度协议为待实现设计，当前工程尚未实现自动粒度选择，也没有据此阻断检索的自动门禁。请求顶层使用 `granularity`，缺省为 `auto`：

| 协议值 | 界面选项 | 主要结果 |
|---|---|---|
| `auto` | 自动 | 系统根据本次任务选择一种或多种具体粒度 |
| `function` | 函数/方法 | 函数或方法实现 |
| `class` | 类/接口 | 类或接口 |
| `module` | 模块 | 职责明确的功能模块 |
| `subsystem` | 子系统 | 聚合多个模块的子系统 |

手动选择决定主要结果粒度；只有用户选择 `auto`（含请求省略后的缺省值）时，系统才作粒度决策。各模式均可混合使用词法、符号、向量、模块和图通道，必要依赖与上下文仍可跨粒度补取。该选择不改变底层解析粒度，也不触发索引重建。服务端拒绝枚举之外的 `granularity` 值并返回参数错误，不能将非法值静默归一化为 `auto`。

```json
{
  "protocolVersion": "code-search/v1",
  "messageType": "search.request",
  "requestId": "req_search_001",
  "repositoryId": "payment-monorepo",
  "granularity": "function",
  "snapshot": {
    "sourceRevision": "git:abc123",
    "indexGeneration": "generation_007",
    "workingTreeRevision": null
  },
  "query": {
    "text": "用户登录失败后在哪里转换成 HTTP 401？",
    "intent": "auto",
    "anchors": [],
    "referenceScopes": []
  },
  "scope": {
    "modules": ["auth", "gateway"],
    "languages": ["typescript", "java"],
    "includeTests": false,
    "includeGenerated": false,
    "includeVendor": false
  },
  "retrieval": {
    "strategies": ["lexical", "symbol", "module", "semantic", "graph"],
    "maxSeedSymbols": 20,
    "maxCandidates": 100,
    "maxGraphDepth": 3,
    "maxGraphNodes": 80,
    "maxNeighborsPerNode": 20,
    "allowedRelations": ["CALLS", "THROWS", "HANDLES", "RETURNS", "IMPLEMENTS"]
  },
  "budget": {
    "maxLatencyMs": 3000,
    "maxTokens": 4000,
    "maxSourceLines": 300,
    "maxFiles": 30,
    "maxEdges": 150
  },

### 6.2 `SearchResponse`

响应通过 `routing` 回显粒度决策：`requestedGranularity` 保留规范化后的请求值，`resolvedGranularities` 仅包含 `function`、`class`、`module`、`subsystem` 中的具体粒度，`source` 为 `user` 或 `automatic`，`reason` 说明选择依据。手动模式的主要结果只能采用所选粒度；跨粒度依赖作为上下文证据返回，不计为替代的主要结果。

`confidence` 是可选的自动决策字段，仅在 `source=automatic` 且已校准时返回数值；未知时可省略或为 `null`。手动选择不附带自动决策置信度，也不能被置信度覆盖。指定粒度不可用时，保留请求值与 `source=user`，`resolvedGranularities` 返回空数组，在 `reason`、能力状态及 `warnings` 中显式报告，前端标明不可用，不偷偷改成其他粒度。粒度可用但本次无命中时仍回显该粒度，并返回空结果。

  "nextCursor": null,
  "warnings": []
}
```

## 8. 协议所有权

协议必须标注字段的拥有者，否则后续会出现多个团队同时修改同一字段语义。

| 协议对象 | 权威拥有者 | 消费者 |
|---|---|---|
| 源码快照身份 | Host/Repository Registry | 所有模块 |
| `analysisRevision` | 基础分析块 | 索引服务、模块分析 |
| `graphRevision` | GraphStore 团队 | 模块分析、检索编排 |
| `treeRevision` | Module Tree 团队 | 模块查询、检索编排 |
| `projectionRevision` | Projection 团队 | 在线检索 |
| `indexGeneration` | 发布协调器 | 所有在线查询 |
| 查询预算 | Retrieval Engine | 索引服务和 Context Compiler |
| Agent tool schema | Gateway 团队 | Claude/Codex/OpenCode 等 |
| evidence 语义 | 数据分析和 GraphStore 联合 | Agent、评测系统 |

建议每个字段同时记录：

```text
owner
producer
consumers
required/optional
valid values
compatibility rule
```

## 9. 与团队当前实施计划的具体衔接

### 可以直接采用的部分

团队报告中的以下设计应直接作为协议基础：

```text
repositoryId
analysisRevision
analysisHash
graphRevision
buildProfileId
buildContextId
treeRevision
treeInputHash
projectionRevision
```

以下生命周期也可以直接沿用：

```text
pending → queued → running → succeeded/failed/cancelled
```

但建议将任务生命周期与发布生命周期分开：

```text
任务状态：pending / queued / running / succeeded / failed / cancelled
发布状态：building / validating / ready / active / retired
```

“队列任务成功”不能直接等同于“索引可以被在线查询”。

### 需要补齐的部分

团队报告需要新增以下契约：

```text
1. IndexManifest：在线服务知道哪些层已经 ready
2. SnapshotSelector：在线请求固定读取哪一组 revision
3. LexicalQuery：全文/路径搜索接口
4. SymbolQuery：符号和定义引用接口
5. GraphQuery：邻居、路径和证据接口
6. ContextCompile：token 预算与源码切片接口
7. CapabilityStatus：partial/fallback 能力声明
8. Cursor：大结果分页且绑定查询条件
```

### 不建议现在阻塞的部分

以下能力可以延后，不应阻塞基础在线索引：

```text
完整 SCIP 支持
全语言 compiler-accurate call graph
复杂 CPG
运行时 trace
完整 Web 前端
多租户高级权限
```

首版在线索引只要能稳定提供：

```text
file search
symbol search
module overview
source ranges
basic relations
snapshot consistency
```

就可以开始接入检索编排和真实任务评测。

## 10. 推荐第一阶段的最小协议

如果当前马上开始实现，建议先冻结以下三个 Schema。

### `index-manifest.schema.json`

必须包含：

```text
repositoryId
sourceRevision
analysisRevision
indexGeneration
status
layers
quality
artifacts
```

### `search-request.schema.json`

规范化后的请求必须包含以下字段；外部请求可以省略 `granularity`，由服务端补为 `auto`：

```text
requestId
repositoryId
snapshot
query
granularity
scope
budget
```

`granularity` 枚举为 `auto | function | class | module | subsystem`，属于请求顶层。自动模式实际采用的多种粒度由 `routing.resolvedGranularities` 回显，检索通道组合由 `retrieval.strategies` 表达；不再使用 `query.preferredGranularity` 或 `mixed` 作为粒度值，非法枚举按第 6.1 节拒绝。

### `evidence-response.schema.json`

必须包含：

```text
requestId
snapshot
routing
results
sourceEvidence
truncated
nextCursor
warnings
```

`routing` 必须包含 `requestedGranularity`、`resolvedGranularities`、`source`、`reason`；`resolvedGranularities` 是去重的具体粒度数组，不包含 `auto`。`source=user` 对应手动选择，所选粒度不可用时数组为空；`source=automatic` 仅对应 `requestedGranularity=auto`，可选择多种具体粒度。可选 `confidence` 只适用于自动模式，已校准时取 `[0, 1]`，未知时为 `null` 或省略。能力缺失与无命中必须按第 6.2 节区分。

协议先使用 JSON/HTTP 实现即可。内部如果以后需要高吞吐，再将稳定 Schema 映射到 Protobuf/gRPC。不要一开始同时维护 JSON、TypeScript 类型、数据库字段和 Protobuf 四份独立定义；应使用单一 Schema 生成其他绑定。

## 11. 最终判断

团队报告正在实现的是原规划中的**索引生产线和多粒度知识底座**。它与原规划的差异不是方向冲突，而是层次不同：

```text
团队报告：把代码仓变成可查询、可分层、可增量维护的索引
原规划：把用户问题变成索引调用，并编译成 Agent 可消费的证据
```

因此现在最合理的开发顺序是：

```text
第一步：按团队报告实现流式基础索引和不可变发布
第二步：冻结 IndexManifest、SnapshotSelector 和三类基础查询接口
第三步：实现在线索引数据服务
第四步：在其上实现 Query Planner、图扩展和 Context Compiler
第五步：最后接 MCP、HTTP、CLI 和 IDE 前端
```

最重要的协议原则是：

> **离线模块发布带版本、能力状态、质量覆盖和 artifact 引用的索引快照；在线模块只读取已发布快照，并通过查询预算、分页游标和源码证据向上层提供稳定结果。**

在线模块不应该知道离线索引内部是 SeekDB、RocksDB、Zoekt 还是其他实现。离线模块也不应该知道 Agent 当前需要 2,000 还是 8,000 token。双方只通过 snapshot identity、capability manifest、query budget 和 evidence contract 协作。
